# Story 19.3: Espaider v2 Parent Dataset Incremental Sync

**EPIC:** 19 - Espaider v2 Sync Migration
**Story ID:** 19.3
**Status:** READY
**Assignee:** @data-engineer + @dev
**Priority:** CRITICAL
**Effort:** 2-3 days
**Depends on:** 19.1, 19.2

---

## Goal

Implement the incremental ETL for the parent project dataset from v2 into `projects`, preserving idempotency and safe reprocessing.

---

## Context for Implementation

The parent v2 payload is flattened and no longer comes as `ListaCampos`.

Important fields already confirmed in the sample:

- `IDEspaider`
- `CODIGO`
- `NOME`
- `STATUSPROJETO`
- `SITUACAOATUAL`
- `RESPONSAVELPROJETO`
- `PRIORIDADE`
- `DATAMOVIMENTACAO`
- `DATAINICIOAPROVACAO`
- `PASTACONSULTIVO`
- `CHAMADO_EXTERNO`

Important mapping constraint:

- `PASTACONSULTIVO` can be an object with `ID` and `NumeroCaso`

Important sync constraint:

- incremental filter should use `DATAMOVIMENTACAO_DE` and `DATAMOVIMENTACAO_ATE`

Do not regress to full-sync-only design unless fallback is explicit and documented.

---

## Acceptance Criteria

- [ ] Create v2 sync path for parent dataset only
- [ ] Initial sync window supports full bootstrap fallback
- [ ] Incremental sync uses documented `DATAMOVIMENTACAO_*` filters
- [ ] Parent pagination is fully drained when `URLPaginacao` exists
- [ ] Parent records are mapped into `projects` with idempotent upsert
- [ ] `pasta_consultivo` and `pasta_consultivo_id` are populated from object payload when available
- [ ] Existing uniqueness strategy `tenant_id + espaider_id` is preserved
- [ ] Sync state or watermark is persisted in a project-approved location
- [ ] Errors on individual records do not silently disappear
- [ ] Unit and integration tests cover bootstrap, incremental replay and duplicate prevention

---

## Architecture Notes

Recommended scope for this story:

- fetch parent records
- compute sync window
- map to domain
- persist valid parent rows

Recommended out of scope:

- child datasets
- frontend logs polish
- rollout switch

Recommended persistence behavior:

- use existing `projects` table unless a proven schema gap requires migration
- update `last_sync_at`/status metadata in the integration config as part of orchestration
