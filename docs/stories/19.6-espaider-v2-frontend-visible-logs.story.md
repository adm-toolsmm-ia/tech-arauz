# Story 19.6: Espaider v2 Frontend-Visible Logs and Observability

**EPIC:** 19 - Espaider v2 Sync Migration
**Story ID:** 19.6
**Status:** Done
**Assignee:** @dev
**Priority:** HIGH
**Effort:** 2-3 days
**Depends on:** 19.3, 19.4, 19.5

---

## Goal

Ensure that the v2 sync emits operational logs that remain visible in the existing frontend integration history surfaces.

---

## Context for Implementation

The current product already exposes log history in the integrations frontend via:

- `integration_log_entries`
- `sync_logs`
- `/api/integracoes/logs`
- `/api/integracoes/logs/summary`

The v2 implementation must preserve or improve that visibility.

Operational requirement from the epic:

- log connection attempt
- sync start
- page fetches when relevant
- dataset success/failure
- quarantine counts
- sync end summary

---

## Acceptance Criteria

- [x] v2 sync writes frontend-visible logs using existing or explicitly evolved logging tables
- [x] Each sync run has a correlation key or request_id
- [x] Key events are logged:
  - connection attempt
  - sync started
  - page fetched
  - dataset processed
  - quarantine summary
  - sync completed
  - sync failed
- [x] Log messages are actionable and sanitized
- [x] Existing frontend log viewer can display v2 events without breaking
- [x] Summary endpoints continue to return meaningful status for v2 runs
- [x] Tests cover log persistence and API output for the viewer

---

## Architecture Notes

Preferred approach:

- keep the current frontend-visible log path compatible
- add structure through `details` fields instead of breaking the viewer contract
- avoid inventing a second invisible logging system for v2

If schema evolution is needed for logs:

- make it additive
- preserve backward compatibility for existing UI queries
