## Overview

All mutations and server-side operations execute via **Server Actions** — type-safe, backend-first patterns with implicit auth context (tenant_id isolation via RLS).

**Key Patterns:**
- All actions marked with `'use server'`
- Auth context retrieved via `getAuthContext()` → validates user + tenant_id
- Return type: `ActionResult<T>` with `{ success, message, data }`
- Responses cached via `revalidatePath()` for ISR (Incremental Static Regeneration)
- All mutations validated at DB layer via RLS policies (zero trust model)

#### `getBootstrapTemplatesAction(organizationType)`
- **Purpose:** Fetch pre-configured template for organization type (legal_office, consultancy, corporation, other)
- **Input:** `organizationType: 'legal_office' | 'consultancy' | 'corporation' | 'other'`
- **Output:** `{ success: boolean; message: string; data: BootstrapTemplate }`

  - Throws: Error if invalid organization_type
  - Usage: Initial setup wizard selection

#### `listBootstrapTemplatesAction()`
- **Purpose:** List all available bootstrap templates
- **Input:** None
- **Output:** `{ success: boolean; message: string; data: BootstrapTemplate[] }`
- **Story:** 11.12 Step 2
- **Details:**
  - Returns array of all templates for org types
  - No filtering — full list for UI selection
  - Used in: OrganizationSetup wizard dropdown

#### `validateWizardStepAction(step, data)`
- **Purpose:** Validate data at each wizard step (1-5)
- **Input:** `step: number` (1-5), `data: Record<string, any>` (form data)
- **Output:** `{ success: boolean; message: string; data: { valid: boolean; errors: string[] } }`
- **Story:** 11.12 (Step validation)
- **Validation by Step:**
  - **Step 1:** organization_type required
  - **Step 2:** template_id required
  - **Step 3:** areas[] not empty, each area has name + nuclei, each nucleus has name
  - **Step 4:** processes[] is array (can be empty)
  - **Step 5:** organization_type confirmed
- **Details:**
  - Returns array of error messages if validation fails
  - Error messages localized in Portuguese
  - Used in: Wizard form submission before advancing

#### `createOrgFromWizardAction(wizardData)`
- **Purpose:** Finalize wizard: bulk-insert areas → nuclei → (optional) processes
- **Input:** `wizardData: { organization_type, areas: WizardAreaSetup[], processes?, integrations? }`
- **Output:** `{ success: boolean; message: string; data: { organization_id: string } }`
- **Story:** 11.12 Step 5 (Final submission)
- **Details:**
  - **Algorithm:**
    1. Validate auth context (tenant_id)
    2. Get current organization from organizations table
    3. For each area in wizardData:
       - Insert area with organization_id + tenant_id
       - For each nucleus in area.nuclei:
         - Insert nucleus with area_id + tenant_id
  4. For each process (if provided):
       - Insert process linked to nucleus or area
  5. Return organization_id
  - **Constraints:**
    - All entities scoped to current tenant_id (RLS enforced)
    - Fails if organization not found (multi-tenant check)
    - Cascade creates relationships (area → nuclei → processes)
  - **Cache:** `revalidatePath('/organizations')` after completion

## 🔐 Authorization & Auth Context

All server actions follow this pattern:

```typescript
export async function myAction(input: MyInput): Promise<ActionResult<MyOutput>> {
  // 1. Get auth context (validates user + tenant_id)
  const ctx = await getAuthContext();
  if ('error' in ctx) return { success: false, message: ctx.error };

  // 2. Auth context includes:
  const { supabase, user, tenantId } = ctx;

  // 3. All DB operations include tenant_id (RLS enforced)
  const { data, error } = await ctx.supabase
    .from('org_areas')
    .select()
    .eq('tenant_id', ctx.tenantId)  // ← Tenant isolation
    .single();

  // 4. Return standardized response
  return { success: !error, message: '...', data };
}
```

**Key guarantees:**
- ✅ No cross-tenant data leakage (RLS enforced)
- ✅ User must be authenticated
- ✅ All responses standardized (`success | message | data`)
- ✅ All mutations trigger `revalidatePath()` for cache busting

## 🚀 Performance & Caching

### Cache Invalidation via `revalidatePath()`

After mutations, paths are revalidated to trigger ISR:

```typescript
// After area creation/update/delete:
revalidatePath('/organizacao/areas');
revalidatePath('/organizacao/empresa');

// After nucleus creation:
revalidatePath('/organizacao/nucleos');
revalidatePath('/organizacao/processos');
```

**Benefit:** Stale content served from cache; revalidation happens in background.
