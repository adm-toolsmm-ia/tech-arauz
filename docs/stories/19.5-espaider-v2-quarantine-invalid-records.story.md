# Story 19.5: Espaider v2 Invalid Record Quarantine

**EPIC:** 19 - Espaider v2 Sync Migration
**Story ID:** 19.5
**Status:** READY
**Assignee:** @data-engineer
**Priority:** HIGH
**Effort:** 1-2 days
**Depends on:** 19.2, 19.3, 19.4

---

## Goal

Introduce a quarantine mechanism for invalid v2 records so that the sync remains reliable and every rejected item has a traceable reason.

---

## Context for Implementation

EPIC 19 explicitly requires isolation of invalid items with traceable reasons.

The current logs alone are not enough for reliable reprocessing and audit if a large batch contains mixed valid and invalid records.

This story should prefer a dedicated persistence mechanism over ephemeral console logs.

---

## Acceptance Criteria

- [ ] Invalid parent or child records are isolated instead of silently dropped
- [ ] Quarantine persistence stores:
  - tenant_id
  - request_id or correlation_id
  - dataset
  - stage
  - raw payload
  - validation or processing reason
  - timestamps
- [ ] Sync summary includes quarantine counts
- [ ] Frontend-visible logs mention quarantined counts without leaking secrets
- [ ] Reprocessing strategy from quarantine is documented, even if replay tooling is not implemented in this story
- [ ] Tests cover schema-invalid and processing-invalid scenarios

---

## Architecture Notes

Recommended implementation:

- add a dedicated quarantine table
- write quarantine entries during validation or mapping failure
- do not fail the entire sync run for item-level data defects unless threshold policy requires it

Recommended table name:

- `integration_sync_quarantine`

If another name is chosen, document the reason and keep it integration-scoped rather than project-domain-specific.
