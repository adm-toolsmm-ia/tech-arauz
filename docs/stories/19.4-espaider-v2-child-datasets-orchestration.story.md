# Story 19.4: Espaider v2 Child Datasets Orchestration

**EPIC:** 19 - Espaider v2 Sync Migration
**Story ID:** 19.4
**Status:** READY
**Assignee:** @data-engineer + @dev
**Priority:** CRITICAL
**Effort:** 3-4 days
**Depends on:** 19.3

---

## Goal

Process the inline child datasets returned by `ListaFilhos`, including child pagination, and persist them into the correct project child tables.

---

## Context for Implementation

The sample response confirms 8 child datasets:

- `BI_SOLICITACOES_PROJETOSESPAIDER_TEMPOSPERMANCENCIA`
- `BI_SOLICITACOES_PROJETOSESPAIDER_REQUISITOS`
- `BI_SOLICITACOES_PROJETOSESPAIDER_ORCAMENTOS`
- `BI_SOLICITACOES_PROJETOSESPAIDER_HORASLANCADAS`
- `BI_SOLICITACOES_PROJETOSESPAIDER_HISTORICOS`
- `BI_SOLICITACOES_PROJETOSESPAIDER_ENTREGAS`
- `BI_SOLICITACOES_PROJETOSESPAIDER_CRONOGRAMAS`
- `BI_SOLICITACOES_PROJETOSESPAIDER_APROVADORES`

The implementation must treat these identifiers literally.

Important:

- some children include their own `URLPaginacao`
- child records must be linked using `IDREGISTROPAI` -> parent `projects.espaider_id`
- some current tables have legacy schema inconsistencies and must be handled carefully

---

## Acceptance Criteria

- [ ] `ListaFilhos` processing is implemented in the v2 sync orchestration
- [ ] Each known child dataset is routed by identifier to the correct mapper/persistence path
- [ ] Child pagination is drained when the child container exposes `URLPaginacao`
- [ ] Child records are linked to parent `projects` safely using `IDREGISTROPAI`
- [ ] Orphan child rows are counted and logged, not silently ignored
- [ ] Upserts remain idempotent per child dataset
- [ ] The vendor typo `TEMPOSPERMANCENCIA` is handled literally in routing
- [ ] Tests cover at least one paginated child and one non-paginated child
