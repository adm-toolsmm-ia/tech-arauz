# Story 19.7: Espaider v2 Cutover Controls and Execution Switch

**EPIC:** 19 - Espaider v2 Sync Migration
**Story ID:** 19.7
**Status:** READY
**Assignee:** @architect + @dev
**Priority:** HIGH
**Effort:** 1-2 days
**Depends on:** 19.6

---

## Goal

Introduce the operational controls required to switch execution from v1 to v2 safely and reversibly.

---

## Context for Implementation

The project already has a tenant-scoped integration configuration table with `settings` and active-state metadata.

This story should use an existing configuration surface whenever possible instead of inventing a new control plane.

The main requirement is operational reversibility:

- enable v2 without deleting v1
- disable v2 quickly if needed
- make the selected execution mode explicit in backend logic

---

## Acceptance Criteria

- [ ] The sync orchestration can choose between v1 and v2 execution explicitly
- [ ] The selected version is stored in tenant-scoped integration configuration
- [ ] Default behavior during migration is documented and safe
- [ ] Admin-facing control exists in backend and, if necessary, in integrations UI
- [ ] Rolling back from v2 to v1 does not require code edits
- [ ] Logs clearly indicate whether a run used v1 or v2
- [ ] Tests cover execution selection behavior

---

## Architecture Notes

Preferred control mechanism:

- `espaider_apis.settings` or equivalent tenant-scoped config

Suggested setting examples:

- `settings.api_version = "v1" | "v2"`
- `settings.sync_mode = "full" | "incremental"`

The exact key names may differ, but the design must remain:

- explicit
- tenant-scoped
- reversible without redeploy
