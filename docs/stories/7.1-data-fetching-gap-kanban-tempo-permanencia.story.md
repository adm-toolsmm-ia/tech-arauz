## Notas Técnicas

### Existing Implementation (Verified in v0.2.2)

The feature was implemented with:

**Query Pattern** (src/app/actions/projects.ts:78):
```typescript
select(
  `
  *,
  schedules:project_schedules(*),
  deliveries:project_deliveries(*),
  histories:project_histories(*),
  approvers:project_approvers(*),
  budgets:project_budgets(*),
  tempos_permanencia:project_tempo_permanencia(*)  // ← EXISTING
  `
)
```

**Badge Rendering Pattern** (ProjectKanbanCard.tsx):
```typescript
// Receives tempos_permanencia array from query
const tempo = project.tempos_permanencia?.[0];
const diasNaFase = tempo?.dias_na_fase ?? 0;

// Color mapping
const badgeColor =
  diasNaFase < 15 ? 'bg-green-100' :
  diasNaFase < 30 ? 'bg-yellow-100' :
  'bg-red-100';
```

### Data Flow

1. Server Action (`fetchProjectsWithFiltersAction`) fetches projects WITH tempos_permanencia relation
2. Component receives data with `project.tempos_permanencia` array
3. Badges extract `diasNaFase` and apply color logic
4. Multi-tenant isolation via RLS on projects table (tenant_id enforcement)

### Performance Considerations

- **Relation fetch:** Single query with nested select (no N+1)
- **GIN Index:** `idx_project_time_in_stage_phase` ensures fast tempo lookups
- **Caching:** TanStack Query caches results with stale-while-revalidate strategy

---

## Architecture Decision

- **Query Pattern:** Nested select relation for co-located data (tempo with project)
- **Data Colocation:** tempos_permanencia fetched same query as project (reduces round-trips)
- **Type Safety:** ProjectWithTempos interface includes `tempos_permanencia: TempoRecord[]`
- **RLS Enforcement:** tenant_id check on projects table protects related tempos automatically
- **Backward Compatibility:** tempos_permanencia is optional in UI (?.at(0) safe access)
